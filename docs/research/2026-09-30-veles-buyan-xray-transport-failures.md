# Research: veles → buyan Xray transport failures

## Conclusion (updated 2026-10-03)

**Strong working hypothesis: two independent problems compound the failures.** First, `fingerprint = "randomized"` can produce a bad REALITY ClientHello for the lifetime of an Xray process: in six fresh Mac Xray processes using the same TCP+Vision profile, both attempts succeeded in two processes and both failed in four. Changing only the fingerprint to Firefox made TCP succeed in a separate direct test. This resembles the upstream [randomized uTLS/REALITY HRR bug](https://github.com/XTLS/Xray-core/issues/6714), though no packet capture has proved that exact TLS error here. Second, fresh authenticated handshakes from veles toward buyan are unreliable even with fixed fingerprints: the same Xray 26.9.9 configuration succeeded directly from the Mac with Firefox (6/6 requests), but failed when run natively on veles with Firefox (0/6); Chrome succeeded only once on veles (1/6). This strongly implicates the veles→buyan path or source-dependent treatment, **not necessarily DPI**. The precise drop/rejection point still needs packet or server-log evidence. The deployed observatory continues to rate gRPC healthy and TCP/xHTTP unhealthy, but long-lived gRPC connection reuse is only a possible explanation for that difference, not yet demonstrated.

## Local evidence

- Repeated read-only requests to veles's loopback Xray `/debug/vars` returned `alive=true` for `relay-grpc-out` and `relay-grpc-backup-out` (roughly 113–132 ms), and `alive=false`, delay `99999999`, for `relay-tcp-{,backup-}out` and `relay-xhttp-{,backup-}out`. The configured observatory probes `https://www.google.com/generate_204` every 60 seconds; it cannot by itself distinguish handshake failure from a failed HTTP response. See [`roles/network/xray/default.nix`](../../roles/network/xray/default.nix) and [`roles/network/xray/relay.nix`](../../roles/network/xray/relay.nix).
- Six simple TCP connect attempts from veles to buyan succeeded, three each to ports 443 and 2053. These do **not** prove TLS or VLESS authentication works. TCP/2053 is redirected to the same SNI router as 443; it is not an independent Xray backend. See [`roles/network/sni-router.nix`](../../roles/network/sni-router.nix).
- Direct HTTPS to `ghcr.io`, `update.googleapis.com`, and `dl.google.com` completed TLS from **both** hosts. This does not test those SNIs when paired with *buyan's IP*, or a REALITY-authenticated connection. Unauthenticated `curl` TLS attempts to buyan with each SNI timed out, **including the gRPC SNI**: an invalid REALITY client can follow a different path from an authenticated one, so this test cannot explain the observed transport split. See [Xray REALITY documentation](https://xtls.github.io/en/config/transports/reality.html).
- Veles config uses `ghcr.io` for TCP+Vision, `update.googleapis.com` for gRPC, and `dl.google.com` for xHTTP when connecting to buyan; the three names match buyan's declared inbounds. Both backup and primary candidates use the same transport/SNI, the client fingerprint is `randomized`, and outgoing VLESS ClientHellos use `finalmask.tcp` fragmentation by default. Nginx routes on the *visible* TLS SNI to three different loopback Xray inbounds. See [`machines/veles/default.nix`](../../machines/veles/default.nix), [`machines/buyan/default.nix`](../../machines/buyan/default.nix), and [`roles/network/xray/transports/`](../../roles/network/xray/transports/).

## Controlled cross-vantage probes (2026-10-02)

- A temporary Xray 26.9.9 client used the same REALITY key, short ID, VLESS user, three SNIs, gRPC service name, xHTTP path, Vision flow, and ClientHello fragmentation as the veles relay. It bound only to loopback, issued two authenticated SOCKS requests per transport to the observatory URL, and removed its private configuration and process afterward. With fixed `firefox` fingerprint, **Mac direct → buyan** returned HTTP 204 for TCP, gRPC and xHTTP on all six requests. **Veles native → buyan**, with the same generated config and binary version, yielded 0/6 successes: five curl connection timeouts at the explicitly short **4-second** connection deadline and one TLS failure. With `chrome` instead, veles succeeded on one of six requests (TCP); gRPC and xHTTP both failed twice. This comparison rules out a *universally* broken buyan backend or universally invalid credentials, not a source-dependent server rejection or ordinary path loss. The four-second test timeout means a timed-out handshake might eventually succeed; it is not proof of a hard block.
- In a separate test the Mac ran the same fixed-Firefox client through a temporary SSH TCP forward exiting at veles: all six requests failed, versus 6/6 directly. SSH forwarding was not rejected according to its local diagnostics, but it can resegment ClientHello traffic, so this corroborates an egress-path difference without replicating veles Xray packetization.
- Six fresh Mac processes with `randomized` fingerprint and unchanged TCP+Vision settings each made two requests: process outcomes were **0/2, 2/2, 0/2, 0/2, 2/2, 0/2**. The all-or-nothing clustering across process restarts is consistent with a process-seeded handshake defect rather than an inherently unusable TCP backend. One earlier randomized Mac run failed every transport (0/6); another succeeded on gRPC and xHTTP (4/6). A controlled packet trace or Xray error log would be needed to identify the exact uTLS failure.
- A follow-up fixed-Firefox run on veles allowed **12 seconds** for connection establishment and **20 seconds** overall per request. TCP and xHTTP both timed out at the 12-second connection deadline; gRPC returned a TLS error after 7 seconds (0/3 successes). At roughly the same time a direct Mac Firefox xHTTP control succeeded twice with HTTP 204. This rules out the original four-second test limit as the sole explanation, but still does not identify the loss/rejection point.
- Both running services remained active on veles after the experiments. A subsequent check found no remaining private probe directories there. No service settings were changed.

## Opposite-direction authenticated probes (2026-10-02)

- A second isolated Xray 26.9.9 client used fixed `firefox`, the existing destination-matched VLESS/REALITY settings, and loopback-only SOCKS on **buyan → veles**. A direct **Mac → veles** gRPC control returned HTTP 204 twice (2/2). On buyan, one request per transport through veles returned HTTP 204: TCP+Vision (0.40 s), gRPC (0.42 s), and xHTTP (0.38 s). These HTTP requests **exited via veles**, not buyan; they verify authenticated connection establishment in the direction needed by a proposed buyan-initiated reverse tunnel, **not reverse-tunnel forwarding**.
- A near-contemporaneous isolated **veles → buyan** run with the same Xray version, fixed fingerprint, fragmentation, and a 12-second connect deadline failed all three requests: TCP and xHTTP timed out after 12 seconds, and gRPC returned a TLS error after 7 seconds. Destination server, SNI, and credentials were necessarily different in the two directions; the contrast does **not** isolate direction as the cause or establish DPI. It does show that buyan → veles was usable when veles → buyan was not under these tested profiles.
- Both production Xray services remained active. Temporary probe processes/configurations were removed and neither host had a remaining probe directory. The next discriminating experiment must send a request originating on veles through a **buyan-initiated reverse connection** and confirm both its HTTP result and **buyan egress identity**. See the [reverse-relay proposal](../superpowers/specs/2026-10-03-buyan-initiated-reverse-relay-design.md).

## External evidence and limits

- [Xue et al., IMC 2022, *TSPU: Russia’s Decentralized Censorship System*](https://censorbib.nymity.ch/pdf/Xue2022b.pdf) report Russian filtering mechanisms triggered by SNI, IP, and QUIC in their measurements; their datacenter VPSes showed little or no censorship compared with their residential vantage points, which further limits applicability to veles; [OONI's 2022 Russia measurements](https://ooni.org/post/2022-russia-blocks-amid-ru-ua-conflict/) include TLS ClientHello-triggered resets and timeouts. These show that SNI/handshake-dependent disruption is possible, **not** that the current veles→buyan failure has this cause. The evidence is historical and network-specific.
- [Xray REALITY settings](https://xtls.github.io/en/config/transports/reality.html) require the client SNI to agree with the server's configured names. [Xray TLS documentation](https://xtls.github.io/en/config/transports/tls.html) describes `randomized` as a randomized ClientHello fingerprint, not a normal fixed Chrome fingerprint; uTLS imitation covers ClientHello, not all subsequent browser behavior. [Xray gRPC documentation](https://xtls.github.io/en/config/transports/grpc.html) describes HTTP/2 multiplexing and warns about active probing; the [XHTTP design discussion](https://github.com/XTLS/Xray-core/discussions/4113) describes distinct HTTP modes and connection reuse. Their design guidance does **not** predict which transport survives on this route.
- [Xray-core issue #6714](https://github.com/XTLS/Xray-core/issues/6714) documents a randomized-uTLS ClientHello that advertises `X25519MLKEM768` without an initial share; the REALITY server's valid HelloRetryRequest then triggers an unsupported uTLS path. Its authors report that the bad randomized specification persists for an Xray process's lifetime, while a fixed Firefox fingerprint works. The maintainer advised against `randomized`. This is a close mechanistic match to the process-grouped Mac failures, **not** a packet-level confirmation on veles.
- A [June 2026 roundup of ntc.party reports](https://telegra.ph/Summary--VLESSReality-blocking-in-Russia-last-14-days-May-24--Jun-6-2026-06-06-3) describes mass failures of the then-current Xray `fp=chrome` profile under Russian TSPU; its underlying original thread was not independently retrieved. An [Amnezia report](https://github.com/amnezia-vpn/amnezia-client/issues/2704) says `firefox` restored some `chrome` profiles, but also shows standalone Xray with `chrome` worked on the same phone: it is evidence of client-specific behavior, not proof of a universal Chrome block. Neither source establishes that Firefox bypasses filtering on veles's network.
- Searches surfaced possible first-hand threads at [ntc.party/t/16061/168](https://ntc.party/t/16061/168) and [ntc.party/t/18154](https://ntc.party/t/18154), but the original pages were not retrievable during this investigation. No claims from those threads have been verified; no retrieved measurement demonstrates selective blocking of the three configured names.

## Discriminating tests and mitigation

1. During a failed authenticated TCP or xHTTP request and a successful gRPC control, collect **time-synchronized**, access-restricted packet captures at both veles egress and buyan ingress, plus Xray error and Nginx stream logs. Compare TCP establishment, ClientHello SNI/ALPN, arrival at buyan, server response, retransmissions and reset direction, then the post-handshake request. A ClientHello lost between hosts points to the network path; one arriving at buyan but rejected by the local backend points to routing, REALITY, or transport configuration; a completed handshake followed by stalls points later in the protocol. A reset alone does not prove who injected it. Captures/logs contain sensitive metadata and must not be shared unredacted.
2. Compare the same transport from a non-RU vantage, and try one-variable-at-a-time tests with matched server/router SNI, port, and fingerprint. Merely changing the client SNI without adjusting buyan's SNI router and REALITY server would create an invalid control. Compare fresh and reused connections if failures are intermittent.
3. For immediate service continuity, prefer the two **currently healthy gRPC outbounds** rather than assuming port 2053 is a cure: both ports fail for TCP and xHTTP in the deployed observatory. Test replacing `randomized` with a fixed, supported fingerprint in isolation before any rollout to eliminate the demonstrated process-seeded failure mode; given the June reports, do **not** assume `chrome` is safe on this path. **Do not expect `firefox` alone to fix veles**: an isolated Firefox client there failed at both four- and twelve-second connection deadlines, while Chrome also mostly failed. Restarting the live relay might disrupt its currently healthy gRPC connection. Only if path evidence implicates SNI/ClientHello filtering should matched SNI/fingerprint/fragmentation changes be tried one at a time. If buyan receives and rejects the flow, fix local routing/REALITY instead.

No system configuration was changed or deployed during this investigation. Read-only journal access for the investigating account was unavailable on both machines; two-sided captures and Xray/Nginx error excerpts are still required to identify the precise root cause.
