# Research: declarative Cloudflare authoritative DNS from Nix

## Summary
**Recommend DNSControl, with its `dnsconfig.js` (or IR JSON) rendered from Nix and credentials supplied only at execution time.** It diffs each declared zone against live Cloudflare records on every `preview`/`push`, purges undeclared records by default, needs no Terraform-style durable state, and has separate dry-run and apply commands. It therefore directly fits an existing-zone, authoritative-per-zone DNS-only workflow.

OpenTofu/Terraform is credible and well packaged, but its authoritative scope is the set of records in state, not all records in a Cloudflare zone. It requires a shared, protected state backend plus one-time import/adoption of every record that must be managed; unmanaged live records are outside its deletion semantics. No credible *Nix-native* authoritative-zone reconciler was identified in nixpkgs/NixOS primary sources; the `cloudflare-ddns` NixOS module is a scheduled dynamic-IP updater, not this design.

## Findings

1. **DNSControl has the desired zone reconciliation semantics.** `preview` reads the desired config and live provider configuration and prints corrections; `push` executes the same corrections. Normal domains use `PURGE` by default: records not declared are deleted. `NO_PURGE` prevents deletion but deliberately leaves removed records orphaned; `IGNORE()` is the narrower exception for records intentionally owned elsewhere. Thus declare every intended editable record in a `D("example.com", ...)` and use default purge for an authoritative zone. Cloudflare-maintained SOA, apex NS, and Mail Routing MX/DKIM records are ignored by its Cloudflare provider. [DNSControl commands](https://docs.dnscontrol.org/commands/preview-push) · [NO_PURGE](https://docs.dnscontrol.org/language-reference/domain-modifiers/no_purge) · [IGNORE](https://docs.dnscontrol.org/language-reference/domain-modifiers/ignore) · [Cloudflare provider](https://docs.dnscontrol.org/provider/cloudflareapi)

2. **DNSControl adoption/drift requires no persistent per-record state.** Its preview/push data-gathering phase collects current zones from providers, so the desired file is compared with live Cloudflare data each run. For an existing zone, start with `dnscontrol preview --domains example.com --no-populate`, inspect proposed additions/updates/**deletions**, and iteratively render desired records until the diff is intended before the first `push`; `--no-populate` also prevents accidental creation of a zone that is absent. A scheduled `preview --expect-no-changes` is an effective CI drift check (it exits non-zero on any required change); a separately approved/manual `push` corrects drift. The documented Cloudflare provider limitation is more than 1,000 corrections on one domain in one push, so bootstrap such a zone in batches. [DNSControl commands](https://docs.dnscontrol.org/commands/preview-push) · [Getting started](https://docs.dnscontrol.org/getting-started/getting-started) · [Cloudflare provider](https://docs.dnscontrol.org/provider/cloudflareapi)

3. **OpenTofu/Terraform needs state and only deletes resources it tracks.** State maps configuration addresses to remote objects; default planning refreshes tracked objects and proposes changes to match configuration. A resource removed from configuration is destroyed only when its mapping exists in state. Cloudflare’s import guidance says Terraform must reproduce existing record configuration and import each record into state (the documented `cf-terraforming` flow emits individual imports). Consequently, to adopt an existing zone authoritatively, generate one `cloudflare_dns_record` resource per desired record and import every existing record first. A manually created record that was never imported is not a managed object and will not be deleted by `tofu apply`; this is the material mismatch with authoritative *per-zone* desired state. [OpenTofu state purpose](https://opentofu.org/docs/language/state/purpose/) · [OpenTofu plan](https://opentofu.org/docs/cli/commands/plan/) · [Cloudflare import guide](https://developers.cloudflare.com/terraform/advanced-topics/import-cloudflare-resources/)

4. **OpenTofu handles drift only for state-bound records and needs shared state discipline.** A normal plan refreshes existing managed remote objects, detects differences, and apply restores configured attributes. An externally deleted state-bound record is planned for creation; an externally modified one for update. For local use a local state file works, but GitHub Actions and multiple operators require the same protected remote backend; OpenTofu recommends remote state and backend locking to avoid concurrent applies. Use configuration-driven `import` blocks for reviewable CI adoption, then keep the state backend available to both local and CI applies. `destroy = false` changes removal into “forget,” which is inappropriate for authoritative records. [OpenTofu imports](https://opentofu.org/docs/language/import/) · [OpenTofu resource behavior](https://opentofu.org/docs/language/resources/behavior/) · [OpenTofu state purpose](https://opentofu.org/docs/language/state/purpose/)

5. **Use a scoped Cloudflare API token and inject it at runtime, never through Nix evaluation/build output.** Cloudflare defines `Edit` as CRUD/list access and permits resource restriction to a specific zone. For DNS-only DNSControl, grant the token only `Zone / Zone / Read` and `Zone / DNS / Edit`, scoped to the managed zones; DNSControl documents these exact permissions. The Cloudflare Terraform provider supports `CLOUDFLARE_API_TOKEN` and recommends environment variables for sensitive values. Render only non-secret config from Nix; pass the token in the process environment. For DNSControl, provide an ephemeral `creds.json` (mode 0600) or its documented executable `--creds !program` mechanism, generated at runtime from the environment—never a Nix `writeText` derivation. NixOS itself warns that configuration can be stored insecurely in the global Nix store, and NixOS options commonly use separate secret-file paths to avoid world-readable store material. [Cloudflare token creation](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/) · [DNSControl Cloudflare provider](https://docs.dnscontrol.org/provider/cloudflareapi) · [Cloudflare Terraform provider](https://developers.cloudflare.com/api/terraform/) · [NixOS manual](https://nixos.org/manual/nixos/unstable/options)

6. **GitHub Actions can safely support separate preview/apply.** Store the token as an environment or repository secret and expose it only as a step/job environment variable; GitHub advises against command-line secret passing. Put `push`/`tofu apply` in a protected GitHub Environment with required reviewers, while pull-request CI runs preview/plan without the secret (fork-triggered workflows do not receive secrets). GitHub redacts registered secrets but says masking is not a complete protection, so do not print generated credentials or enable shell tracing. For DNSControl, a practical shape is: PR `preview --expect-no-changes` only if credentials are safely available; protected `workflow_dispatch`/main deployment runs `preview`, then `push`. For OpenTofu, run `plan` and approved `apply` against the same remote state backend. [GitHub Actions secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets) · [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use) · [GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

7. **Nix integration is packaging/rendering, not secret management or reconciliation.** nixpkgs packages both DNSControl and OpenTofu; Nix can deterministically generate the non-secret desired DNSControl DSL/IR or `.tf` files and a local `nix run` wrapper. DNSControl accepts `--ir` JSON directly, which is particularly suitable for generation. The NixOS `services.cloudflare-ddns` module instead continuously updates configured dynamic records every five minutes by default and exposes a credentials file; it is not an authoritative-zone tool and does not meet the separate-apply constraint. [nixpkgs DNSControl](https://github.com/NixOS/nixpkgs/blob/release-26.05/pkgs/by-name/dn/dnscontrol/package.nix) · [nixpkgs OpenTofu](https://github.com/NixOS/nixpkgs/blob/3dec6b45/pkgs/by-name/op/opentofu/package.nix) · [DNSControl commands](https://docs.dnscontrol.org/commands/preview-push) · [NixOS cloudflare-ddns module](https://github.com/NixOS/nixpkgs/blob/ed142ab1b3a092c4d149245d0c4126a5d7ea00b0/nixos/modules/services/networking/cloudflare-ddns.nix)

## Recommendation
Adopt **DNSControl + Nix-generated non-secret configuration**. Make each existing Cloudflare zone a full desired `D()` declaration, preserve only explicit exceptions with `IGNORE()`, and require `--no-populate` in all operational commands. Provide two local commands: `dns-preview` (live diff; CI can use `--expect-no-changes`) and `dns-apply` (`preview` followed by explicitly authorized `push`). On CI, make apply a protected Environment deployment and inject a zone-scoped `CLOUDFLARE_DNS_TOKEN` only at runtime to create temporary credentials. This offers exact authoritative-zone deletion and drift repair without remote state.

Choose OpenTofu only if the team already operates a secure, locked remote state backend and accepts resource-level—not native zone-level—authority, including comprehensive initial import and continued adoption of out-of-band records. Do not choose `cloudflare-ddns` for this purpose.

## Gaps
- This note does not test a generated configuration against the repository’s pinned nixpkgs revision or select the exact flake/package wiring.
- Confirm Cloudflare token resource selection supports the precise set of production zones in the dashboard before rollout, and retain/export a zone backup before the first authoritative push.
- DNSControl’s Cloudflare provider documents a >1,000-correction push limitation; large initial convergence needs a staged migration.
