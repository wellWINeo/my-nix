# Buyan-Initiated Xray Reverse Relay Design

**Status:** Approved design for a staged rollout; not implemented or deployed. Configuration validity, reverse forwarding, and failover must be demonstrated with the deployed Xray binary before considering the rollout successful.

## Goal and scope

Make Buyan initiate the inter-server connection to Veles while retaining Buyan as the public internet egress for **Veles relay traffic**:

```text
client -- TCP/gRPC/xHTTP/Hysteria2 --> Veles relay inbound
                                          | reverse-first (Buyan-initiated xHTTP over TCP)
                                          v
                                      Buyan --> public TCP/UDP destination
                                          |
                          fallback: Veles -- existing gRPC outbound --> Buyan
```

The client-facing protocol is independent of the reverse link's xHTTP transport. Proxied UDP, when supported by this exact reverse configuration, is carried over the TCP-based inter-server link and sent onward as UDP by Buyan. Only Veles's relay inbounds change routing: `socks-relay-in`, enabled `vless-*-fwd-in` inbounds (including the gRPC tag `vless-grpcFwd-in`), and `hy2-relay-in` when enabled. Its direct server inbounds remain routed to `direct-out`. Buyan's existing public server inbounds and their ordinary egress remain unchanged. NixPi, subscriptions, client credentials, DNS and public listeners are out of scope.

An isolated authenticated Buyan → Veles xHTTP probe returned HTTP 204 in the [local measurements](../../research/2026-09-30-veles-buyan-xray-transport-failures.md); it exited at Veles, so it **did not** establish reverse forwarding or Buyan egress. The [September survey](../../research/2026-10-02-september-2026-xray-filtering-and-settings.md) also rules out treating a fingerprint or transport change alone as a reliable cure. This design is a testable proposal, not a claim that reversing direction defeats the current failure.

## Topology and authentication

Veles is the **portal** and Buyan the **bridge/egress**, following Xray's [VLESS reverse-proxy home-egress example](https://xtls.github.io/en/document/level-2/vless_reverse.html#home-broadband-egress). Veles accepts a dedicated reverse-only VLESS UUID **only** on its existing server xHTTP+REALITY inbound `vless-xhttp-in` (`vk.ru` SNI, configured server xHTTP path, TCP/443 via the existing SNI router). The matching inbound `settings.clients[]` entry has `reverse.tag = "reverse-buyan-out"`; it must not be added to `roles.xray.server.users`, relay users, or subscriptions. The portal's existing ordinary `direct-out` stays the first static outbound so a dynamically registered reverse outbound never becomes its default.

Buyan has a dedicated, explicitly tagged VLESS outbound to `secrets.ip.veles.address:443`, using that UUID, xHTTP+REALITY, the server's matching `vk.ru` SNI and xHTTP path, its REALITY public key and authorized short ID, and a fixed `firefox` fingerprint (not `randomized`). The outbound has `settings.reverse.tag = "reverse-veles-in"`, creating a logical inbound on Buyan. The local reverse tags need not match. Reuse the repository's existing optional ClientHello-fragmentation setting for the new outbound; test the actual chosen transport and fingerprint together, rather than changing any existing relay outbounds.

**Use the simplified VLESS outbound settings** (`address`, `port`, `id`, `encryption = "none"`, `reverse`) for Buyan's reverse client. In [Xray 26.9.9's VLESS parser](https://github.com/XTLS/Xray-core/blob/v26.9.9/infra/conf/vless.go), `reverse` inside the existing `vnext[].users[]` style is rejected. Do not silently reuse `mkVnextOutbound`; copy only the required xHTTP/REALITY stream settings or make a narrowly scoped builder for this one outbound. No new SNI-router entry, public port, second Xray instance, or new dependency is required.

Provision **one new dedicated UUID** as an encrypted file-based secret on both hosts. Add its filename to `secrets/unlocked/spec.txt` for Veles and Buyan, install as `0400 root:root`, and use systemd `LoadCredential` to provide it to the Xray service. The Nix-generated JSON template contains no real reverse UUID; runtime injection populates only the intended Veles xHTTP client and Buyan reverse outbound. Read the credential at process start, validate it as a UUID, and make the rendered runtime JSON readable only by the service user (`umask 077` before writing). Never emit the UUID or rendered config into logs, the Nix store, test output, or chat. This credential is not part of `secrets.singBoxUsers`.

## Routing, egress policy, and failover

On Veles, replace the relay inbound rules' target with one dedicated `reverse-first-balancer` selecting only the dynamically registered `reverse-buyan-out` and setting `fallbackTag = "relay-grpc-out"`. Keep the existing `relay-balancer` and all its regular outbound candidates intact for rollback; do not mix the regular candidates into the reverse selector because `leastPing` would not guarantee a reverse-first trial. Preserve the server rules to `direct-out` and the ordering so only relay inbound tags can select the reverse-first balancer. Xray's `fallbackTag` accepts a **single outbound tag**, not another balancer: see the [routing documentation](https://xtls.github.io/en/config/routing.html#balancerobject) and [26.9.9 implementation](https://github.com/XTLS/Xray-core/blob/v26.9.9/app/router/balancing.go).

Use a health-aware strategy with the reverse tag in Veles's observatory subject selector; retain observation of existing `relay-*` outbounds. Xray dynamically creates the reverse outbound only after Buyan connects. The primary must be preferred while healthy; when absent or marked unhealthy, **new requests** should select `relay-grpc-out`. This is conditional on testing the behavior of the exact deployed binary: an unobserved reverse candidate can initially be treated as healthy, health checks take time, and an existing stream or a failed request is **not** retried automatically. Do not assume a successful TCP connect, a live mux worker, or an HTTPS observatory result proves UDP forwarding. If failover to the named gRPC outbound cannot be shown end to end, do not cut over relay routing. There is no fallback beyond `relay-grpc-out`; a failure of both paths is an error, not permission to exit directly from Veles.

On Buyan, route **only** traffic from `reverse-veles-in` to a dedicated tagged `freedom` outbound, `reverse-public-out`, with no destination rewrite or `sockopt.dialerProxy`. Its `settings.finalRules` explicitly allow `"network": "tcp,udp"` with `"ip": ["!geoip:private"]`; nonmatching targets remain blocked by Xray's reverse-proxy default policy. Xray's [Freedom documentation](https://xtls.github.io/en/config/outbounds/freedom.html#finalruleobject) describes pre-/post-dial checks for domain targets and per-packet UDP checks. Validate with real attempts that loopback, RFC1918, link-local and other non-public/reserved targets (including private-address DNS answers) cannot be reached; if the tested `geoip:private` set does not cover a required reserved range, add a specific deny rule before rollout. Keep Buyan's existing `direct-out` and public VLESS routing unchanged.

## Repository changes and boundaries

- `roles/network/xray/server.nix`: optionally append the reverse-only client to **only** the server xHTTP inbound; do not extend the general users list.
- `roles/network/xray/default.nix`: own minimal reverse options/config on the portal or bridge, compose the reverse outbound and egress rule without a shallow `_extraConfig` override of `routing`/`inbounds`, include the reverse tag in observatory selection, and extend the existing `LoadCredential` + runtime `jq` flow. Keep the ordinary `direct-out` first on both hosts.
- `roles/network/xray/relay.nix`: use the reverse-first balancer only for relay inbound routing when opted in. Retain the existing balancer, tags and outbounds and assert that `relay-grpc-out` exists when this mode is enabled.
- `machines/veles/default.nix`, `machines/buyan/default.nix`: opt in only on the corresponding portal and bridge; use Veles's existing xHTTP server SNI/path and installed REALITY settings. Do not alter the old Veles → Buyan relay fingerprint, transport candidates, or credentials as part of this change.
- `secrets/unlocked/spec.txt`: declare the same reverse UUID filename for both hosts. The secret **contents** are created, encrypted and installed by the operator, not committed in plaintext.

Prefer these existing modules to a general-purpose reverse framework, a watchdog or new public listeners. Any enabling option needed for staged activation should be narrowly scoped to this rollout and default off on other hosts.

## Verification and deployment gates

1. **Before activation:** evaluate both hosts with dummy secrets (`make setup-dummy-secrets` if needed; never overwrite unlocked real secrets), run `make check`, and inspect the generated templates for exactly one reverse client on Veles's server xHTTP inbound, one simplified reverse outbound on Buyan, correct tag/rule ordering, public-only egress policy, explicit fallback and no reverse UUID in the Nix store. Run the **deployed** Xray binary's config validator against securely rendered configs on both hosts; `nix flake check` alone does not prove Xray compatibility. Recheck the installed binary version because `pkgs.xray` comes from a moving unstable input.
2. **Stage without rerouting users:** in an approved maintenance window, install the encrypted-file credential on both machines, enable Veles's dedicated reverse client, then enable Buyan's reverse outbound and egress rule. Confirm the Buyan → Veles connection and dynamic reverse outbound are present; this proves only link establishment. A restart of either Xray service can interrupt existing sessions, especially Veles's currently working gRPC route. Do not deploy without operator approval.
3. **Controlled cutover:** enable reverse-first routing **only** for Veles relay inbounds. Use real HTTPS requests through the existing relay SOCKS and at least one client-facing relay inbound. Require successful HTTP responses and independently confirm the public source address is Buyan's, not Veles's; compare with a Veles-direct control and use per-tag metrics/logs to distinguish reverse from the same-Buyan-IP fallback. Test several fresh connections, not only a reused connection. Test proxied UDP (for example, a controlled DNS or QUIC request) separately and verify both response and Buyan-side egress. A successful TCP probe alone does not validate UDP.
4. **Failure/recovery:** stop or disconnect the Buyan reverse client during an approved test. After bounded health detection, establish *new* relay requests and verify they succeed via `relay-grpc-out` and still exit at Buyan. Verify Veles direct-server inbounds are unchanged and never selected by the reverse-first rule. Restore Buyan, verify the reverse route is selected again using observed egress/routing evidence, and repeat for TCP and UDP. Do not infer reverse-path use from Buyan's IP alone because fallback also exits at Buyan; inspect per-tag metrics/logs without publishing credentials. Record detection time, failed requests and dropped sessions. Test deny rules against loopback/private/link-local targets via the reverse route.
5. **Rollback:** if Xray config validation, reverse forwarding, UDP policy, health selection or recovery fails, revert Veles's relay rules to the existing `relay-balancer` (previous NixOS generation/config) and confirm relay operation. Buyan's reverse link can then be disabled independently. Never substitute Veles's `direct-out` as an implicit fallback. Keep captures, source IPs and runtime configs access-restricted; publish only sanitized results.

## Limits

The Buyan-initiated setup avoids Veles initiating the inter-server handshake, but all bidirectional packets still cross the same international path. Automatic health-based fallback is **best effort for subsequent requests**; it is neither instant nor a replay mechanism. The external Xray reverse example uses a different encrypted VLESS variant and is not proof of this version's xHTTP+REALITY or UDP behavior. The initial implementation must validate these combinations and failover on the deployed Xray version before any claim of a working replacement.
