# Proxy VPS provisioning with nixos-anywhere — design

## Goal and scope

Install a new proxy VPS from a remotely accessible NixOS live ISO with a short operator workflow. The first real installation is a new Timeweb host, `stribog`. Make the existing proxy VPS configurations, `buyan` and `veles`, installable by the same workflow, but do not reinstall, switch, or otherwise modify the live machines as part of the pilot.

`stribog` runs Buyan's proxy role set and Veles's Timeweb-style network and storage profile: DHCP, BIOS/GRUB, ext4 root labeled `NIXROOT`, and a 2 GiB swapfile. It uses the same file-based Reality private key as Buyan and Veles. A new line for `stribog` in `secrets/unlocked/spec.txt` installs that same source file. Its Xray user list uses the existing hostname filter; users explicitly restricted to other hosts are not automatically added to `stribog`.

Out of scope: `mokosh`, `nixpi`, DNS changes, provider API provisioning, changes to `images/do-generic` or the current image generation, a new secret-management system, and installation or switching of the live `buyan`/`veles` hosts.

## Architecture and file ownership

- `flake.nix` pins Disko as an input, imports its NixOS module for `buyan`, `veles`, and `stribog`, defines `nixosConfigurations.stribog`, and adds a separate `devShells.<system>.provision`. The existing default shell remains unchanged. The provision shell includes `pkgs.nixos-anywhere` from the pinned nixpkgs; this package was checked to exist for `aarch64-darwin`. Do not add a second nixos-anywhere flake input.
- `machines/{buyan,veles,stribog}/disk.nix` owns each host's disk layout, mount points, and BIOS boot disk. These are host-specific rather than derived from an Ansible inventory; the disk path can be edited per host before a reinstall. Disko supplies NixOS filesystem and boot settings used by subsequent rebuilds. For existing hosts, preserve the current `NIXROOT`/`NIXSTORE` mount labels and GRUB disk paths in evaluated configuration; do not run Disko against them during the pilot. An explicit evaluation comparison against the current configuration is required before the conversion is accepted.
- `machines/stribog/default.nix` owns DHCP, hostname, SSH policy, guest integration, swapfile, and Buyan-style Xray server, SNI router, observability agent, and Tailscale settings. Its flake entry imports the existing operator user, common modules, and Xray overlay as for Buyan. No relay, MTProxy, or stream-forwarder from Veles is enabled.
- `provision/install.sh` is the only provisioning orchestrator; it handles local checks, live-ISO SSH preparation, temporary secret staging, destructive-action confirmation, invocation of nixos-anywhere, and post-reboot checks. `Makefile` only delegates to this script via `make provision HOST=stribog IP=...`. There is no `provision/ansible/` implementation. The existing image generation stays at `images/do-generic/`; the requested `provision/image/` location is reserved for a separate future move, not created or modified in this work.
- `README.md` documents prerequisites, the pilot command, disk destruction, recovery, and the fact that the other proxy VPS configurations are prepared but not tested on real machines.

## Disk and network

Install all three hosts as BIOS/GRUB systems only. Disko layouts contain the partitioning needed for BIOS GRUB (including an EF02 BIOS boot partition if using GPT) and ext4 labels matching the existing mounts. Buyan has `NIXROOT` on `/` (8 GiB) and `NIXSTORE` on `/nix` (remaining space), with a minimum 16 GiB disk so the 2 GiB root swapfile fits; Veles and Stribog use a single `NIXROOT` filesystem and a 2 GiB swapfile, with a minimum 8 GiB disk. Existing host configurations keep their current network policies: Buyan's static address on `ens3` comes from locally decrypted `secrets/secrets.json`; Veles and Stribog use DHCP; Stribog also inherits Veles's Timeweb IPv6-disable sysctl because IPv6 performs poorly there. Network access in the ISO is a prerequisite and is not derived from the installed system's network configuration.

Before any Disko phase, inspect the actual target device on the live ISO and fail unless it matches the selected host's Disko configuration, exists as a whole disk, has sufficient capacity for the selected layout and swap, and the ISO booted in BIOS mode. Display its path, size, and partition table. Require the operator to enter the hostname and disk path to confirm that all contents of that disk will be destroyed. Never infer a disk from the first available block device.

## Credentials and installation

The operator boots a NixOS live ISO, brings up networking, sets the ISO's short-lived `nixos` SSH password, and invokes the wrapper from a controller with Nix and GPG. Locally decrypted `secrets/secrets.json` is required for flake evaluation; the file secrets and `secrets/unlocked/spec.txt` are required for staging. Refuse to repartition if any expected file is missing. Stage only file secrets referenced by enabled roles on the selected proxy host; require each needed file to have an entry for the host or `*` in the spec, which supplies its mode and ownership. On Buyan and Stribog the needed files are `xray-reality-private-key` and `tailscale-auth-key`; Veles additionally needs `hysteria-veles-key` and `hysteria-veles-cert`. Do not stage unrelated wildcard entries or Veles's stale `cloudflare.ini` entry: Veles has no `acme` account or enabled Let's Encrypt role. Stage in a temporary directory outside the repo, mirroring `/etc/nixos/secrets/`, with restrictive permissions. Respect the selected entries' declared ownership and mode on the installed host; do not print their contents, add them to Git, or bake them into a Nix expression. Clean up the staging directory on exit. Use `--extra-files` to copy them to the target before `nixos-install` activates the full configuration.

Use one temporary installer SSH key for every nixos-anywhere phase. First, SSH as `nixos@ISO_IP` with the ISO's short-lived password and explicitly install that public key for root on the live ISO; verify root login before touching the disk. Then run `--phases disko` as root (no redundant kexec on an already booted NixOS installer), create and enable the 2 GiB `/.swapfile` on the mounted target root for installation-time swap, and run `--phases install,reboot` as root with `--build-on remote`. Reuse the same installer key across phases. The wrapper's resume mode repeats the password-authenticated root-key bootstrap before install without repartitioning. The installed full flake configuration provides `o__ni` with its existing SSH authorization and disables SSH password login; no temporary installed `nixos` account or generated installed-system password is needed. Readiness means the host boots, `o__ni` can SSH in, and required proxy and networking services start with their file secrets present.

A remote Linux builder is not required for the pilot. The controller is an Apple Silicon Mac; the 1 GiB VPS builds its x86_64-linux closure remotely with swap and normal binary caches. Missing substitutes or out-of-memory errors can still block installation. Do not silently retry a destructive Disko phase after a failure; document how to inspect the still-running ISO, its mounts and logs, and retry installation without wiping again when appropriate.

## Security boundary

`--extra-files` only ensures runtime secret files are present at installation; it does not prevent locally decrypted files from entering a flake snapshot. The existing `path:.` flake snapshot was observed to contain both `secrets/secrets.json` and a decrypted Reality private key from `secrets/unlocked/`. The owner explicitly accepts retaining this existing secret model for this provisioning work; do not claim that the flake build or remote Nix store excludes these files.

The inspected nixos-anywhere implementation sets `StrictHostKeyChecking=no` and `UserKnownHostsFile=/dev/null` for its SSH calls. The wrapper should independently check the live ISO's SSH host-key fingerprint against a value the operator verifies out-of-band before destructive work, but this preflight cannot enforce per-connection host-key verification within nixos-anywhere. Document this limitation rather than promising stronger protection. Do not bypass an unexpected mismatch during the preflight.

## Verification and rollout

1. Locally validate Nix formatting and `nix flake check` using available secrets (use dummy JSON only if real JSON is not unlocked, without overwriting a real decrypted file). Evaluate the three host outputs and assert the intended filesystem labels, boot disks, DHCP/static networking, hostnames, proxy roles, and `stribog` users. Compare Buyan and Veles's runtime boot and filesystem options before and after Disko integration; a change to their effective values is a failure.
2. Test the wrapper's non-destructive paths without a VPS: unknown host, missing secret, mismatched disk, UEFI, failed fingerprint verification, and cancellation must exit before Disko. Check shell syntax. Where a Linux VM/test runner is available, run Disko's install test for Stribog; the absence of a builder on macOS must not be represented as a passing test.
3. Install only Stribog on a disposable Timeweb VPS. Confirm post-reboot SSH as `o__ni`, DHCP, `NIXROOT`, swap, relevant `/etc/nixos/secrets/*` ownership/modes, and Xray/SNI-router/observability/Tailscale service health. A representative proxy connection requires at least one user allowed on `stribog`; if no actual user passes the hostname filter, update the encrypted user list before installation or limit the smoke test to service startup.
4. Leave Buyan and Veles untouched until a separately approved real-host reinstall. Record the pilot results and any deviations before using the installer on another host.
