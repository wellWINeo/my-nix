# Veles Timeweb CDN XHTTP Design

**Status:** Proposed; no configuration changes or deployment. This adds an optional client path to the [existing proposed reverse relay](2026-10-04-xray-proxy-simplification-design.md), which has its own [deployment runbook](../../xray-reverse-deployment.md) and is not assumed to be live.

## Goal and boundaries

Add an authenticated, VLESS-encrypted XHTTP ingress on Veles reachable through Timeweb Cloud CDN's issued `*.cdn.twcstorage.ru` hostname. Use `sunny-bee-on-the-flower.net.by` as the HTTPS origin, with an automatically renewed Let's Encrypt certificate. Serve a small static webpage to unauthenticated visitors. Traffic entering this new inbound uses the same Veles reverse balancer and Buyan public egress as existing ordinary clients.

Keep Veles's existing REALITY RAW, gRPC and XHTTP inbounds, Hysteria2, SNI-router rules, UDP listener and TCP/2053 redirect unchanged. Buyan's two reverse connections continue to dial Veles's IP and existing REALITY RAW/XHTTP inbounds directly; Buyan's public inbounds are unchanged. NixPi retains its direct Veles address, REALITY transports and backup port. No existing client is automatically moved to the CDN. No second Xray or Nginx instance, additional public port, preset system, Cloudflare DNS declaration, DNS API integration, CDN alias, or new dependency is needed.

**Limit:** An A record for the origin and the preserved direct endpoints expose Veles's IP. This design hides that address from clients who only receive the Timeweb-issued CDN hostname; it does not hide the origin from DNS lookup or determined discovery. A static page reduces conspicuous responses to casual probes, not the ability of an informed adversary to find or fingerprint a known proxy path.

## Data flow and domain control

```text
New client -- TLS + XHTTP packet-up/GET --> <issued>.cdn.twcstorage.ru
  -- Timeweb HTTPS origin request --> sunny-bee-on-the-flower.net.by:443
  -- existing Veles Nginx stream/SNI router --> 127.0.0.1:9443 (same Nginx, HTTPS)
  -- HTTP proxy --> 127.0.0.1:9013 (new Xray XHTTP/VLESS-Encryption inbound)
  -- existing reverse balancer --> Buyan --> public internet

Buyan -- direct IP + existing REALITY RAW/XHTTP --> Veles:443 (unchanged)
NixPi/old clients -- direct IP + existing transports --> Veles (unchanged)
```

The operator delegates `sunny-bee-on-the-flower.net.by` to **Timeweb DNS** and creates an apex A record to Veles's existing public IPv4 address. Do not publish an AAAA record to Veles while IPv6 is disabled there. Timeweb CDN uses the apex domain as its HTTPS **origin** and issues its own `*.cdn.twcstorage.ru` delivery hostname; clients use that issued hostname as address and TLS SNI. Origin and delivery names must not be aliases of one another. No custom distribution subdomain or edge certificate is required. Do not add this zone to this repository's Cloudflare-only `dns/` declarations.

Timeweb's documented CDN methods are GET/HEAD/OPTIONS. A CDN client must use XHTTP `mode = "packet-up"` and `uplinkHTTPMethod = "GET"` instead of the Xray default POST. The Veles inbound uses `packet-up` with compatible upload-payload handling; `uplinkHTTPMethod` itself chooses the method on the **client** and is not a Timeweb-specific server switch. Use the dedicated XHTTP path `/vl-cdn`; verify Nginx routes only this exact path and its session subpaths, and test the client's payload placement and size limits against the pinned Xray 26.9.9 binary and live Timeweb edge. The client config for a human-operated trial is documented separately, not activated on NixPi. No provider-specific Xray preset is added.

In the Timeweb panel, enable HTTPS to the domain origin and ensure origin-pull is ordinary HTTPS, without a CDN-supplied PROXY header (the Veles SNI router already adds one); disable caching, browser caching, always-online, HTTP/3 and large-file slicing where available; do not override origin no-store headers. Avoid enabling compression for the XHTTP path. Provider support for long-lived GET downlinks, GET uplink payloads/headers, idle timeouts, and disabled caching **is not established by the docs** and is a live feasibility gate. Do not claim success from a `curl /` response alone.

## Veles components

- `machines/veles/default.nix` enables a proposed `roles.xray.relay.ingress.vless.cdnXhttp` group with `originDomain = "sunny-bee-on-the-flower.net.by"`, `path = "/vl-cdn"`, and `decryptionFile = "/etc/nixos/secrets/vlessenc-decryption-key"`. Existing `ingress.users` are reused; no separate CDN user list or role-wide behavior change. This is a proposed option, not an existing one.
- `roles/network/xray/relay.nix` adds one loopback-only VLESS/XHTTP inbound (`127.0.0.1:9013`, distinct tag) to the existing Xray process. Its XHTTP transport has no REALITY or TLS on the loopback hop; VLESS `settings.decryption` is populated from a runtime credential. Its clients are the existing **ordinary** relay users, explicitly excluding the `buyan` reverse-only user. Route the new inbound through the existing reverse balancer and `blocked-out` fallback in reverse mode, and through the existing forward balancer in manual-forward mode. Do not grant it unrestricted/direct egress or create another reverse portal.
- The same relay role owns the new HTTPS origin configuration in the already-running Nginx service. The existing stream listener stays on public TCP/443, routing the origin SNI to the new `127.0.0.1:9443` **HTTPS** listener. This Nginx HTTP listener must accept the PROXY protocol sent by the stream router; it must not listen on public 443 or collide with the existing stream listener. A public HTTP/80 listener supplies the HTTP-01 ACME challenge. NixOS `services.nginx.virtualHosts.<origin>.enableACME` issues and renews the origin certificate and automatically reloads `nginx.service` after successful issuance/renewal; set ACME terms and the existing operator contact `stepan@uspenskiy.su` on Veles. Do not use `roles.letsencrypt`, which provisions Cloudflare DNS-01 certificates for other domains.
- Nginx serves a minimal static HTML landing page for `/`, a static generic 404 for unrelated paths, and proxies only the dedicated XHTTP prefix to the new loopback port. Configure streaming response and request handling (`proxy_buffering off`, `proxy_request_buffering off`, no proxy cache, suitable read/send timeouts); send `Cache-Control: no-store` on dynamic responses. Intercept only expected invalid XHTTP 4xx replies as a generic static 404 so a malformed probe does not receive an Xray-specific error page. Successful 200 streaming responses are not intercepted. Verify that no redirect or caching of the authenticated stream is introduced. The page is static and local; do not proxy an external website or introduce another web service.
- Veles's existing fail2ban Nginx jails can ban a Timeweb edge address after repeated origin errors, disrupting all clients behind that edge. Do not blanket-allowlist undocumented CDN IP ranges or disable the existing jails. Observe Nginx upstream errors and each Nginx jail during controlled CDN tests; an edge ban is a stop condition requiring a narrowly scoped origin-log/jail fix and retest before any client migration.
- `roles/network/xray/default.nix` extends the existing systemd `LoadCredential` and private runtime JSON-rendering step to insert the VLESS decryption value only for the new inbound, before the existing `xray run -test -format json` startup guard. Keep an invalid, non-secret sentinel in the store-backed template and load the credential from its file into the private runtime JSON without putting the value on a process command line (for example, jq `--rawfile` with only a trailing newline removed). A missing or invalid file must fail the guarded startup rather than activating an unencrypted CDN inbound; do not log the value or write it into Nix source. Leave existing REALITY and Hysteria credential dispatch alone.

The CDN-facing client configuration uses the matching generated VLESS `encryption` parameter (not `"none"`), an ordinary Veles user UUID, XHTTP `packet-up`/GET, the new path, and normal validated TLS to the issued Timeweb hostname. The CDN can see TLS termination, host, URL and HTTP headers but should not be able to read the inner VLESS payload or framing. Client and server encryption values must form one matching pair; `xray vlessenc` generates them. Do not silently treat the outer TLS as end-to-end protection from Timeweb.

## Validation and operator rollout

1. Before code changes, establish the existing evaluated baseline in an isolated checkout with **dummy** secrets; never overwrite an ignored real `secrets/secrets.json`. Add regression assertions to `roles/network/xray/tests/reverse.sh` before implementing the new option. Check the new inbound's address, tag, unique port, users, `packet-up` mode, non-REALITY security and runtime decryption injection; check its routing in reverse and manual-forward modes. Assert old Veles/Buyan/NixPi transports, credentials, direct address, and SNI mappings remain unchanged. Assert the origin HTTPS/PROXY-protocol and ACME HTTP/80 listeners do not bind public HTTPS a second time; inspect Nginx static/fallback, response no-store and XHTTP proxy handling. Run `nixfmt` on changed Nix files, `make check`, the Xray role test, and `git diff --check`. Offline evaluation is not a real CDN or encrypted Xray runtime test.
2. Prepare Timeweb DNS delegation, apex A record (without invalid AAAA), origin settings and issued CDN resource; confirm propagation, port 80 reachability, and a working operator-controlled rollback/generation. Do not configure Cloudflare DNS or move any clients. Produce the implementation and client-profile instructions **without** generating a production encryption pair.
3. **Last implementation/handoff step, owned by the human:** use the deployed Xray version's `xray vlessenc` to generate the matched VLESS pair privately; place the server decryption value into the existing encrypted-file secret distribution/install flow at `/etc/nixos/secrets/vlessenc-decryption-key`, with restrictive permissions, and retain the client encryption value privately for a test profile. Do not paste either value into Git, test fixtures, chat, logs, or the Nix store. The agent does not generate the pair. This step must precede activation; it is not the last *operational* step.
4. **Separate operator-approved deployment/live gate, after the handoff:** verify the installed file before switching Veles, build and activate its config with recovery access, check NixOS HTTP-01 issuance, certificate validity, Nginx reload/`nginx -t`, rendered `xray run -test -format json` and both services' status without printing credentials. Visit `/` and unrelated paths via both apex and Timeweb-issued edge, then use an actual VLESS-encrypted GET/packet-up client over the edge. Exercise small and sustained TCP upload/download, idle recovery, UDP through the proxy, uncached per-request behavior, and Buyan's actual egress/source IP. Verify Buyan still dials Veles directly, its reverse tags stay healthy, existing Veles REALITY/Hysteria inbounds work, NixPi remains direct, no Timeweb edge is banned by a Veles Nginx fail2ban jail, and new clients still fail closed when reverse links are unavailable. Verify the renewal timer and automatic Nginx reload path after a successful renewal. A 200/400 from an unauthenticated curl alone is not a proxy test.
5. If the CDN buffers, truncates, rewrites or caches requests, or a service/direct path regresses, do not cut over any client. Roll Veles back to the recorded working NixOS generation and recheck its original direct traffic; disable the trial CDN resource as appropriate. Do not weaken VLESS encryption, bypass certificate verification, add an automatic direct fallback, or alter Buyan/NixPi to make a failed trial appear successful.

No real key generation, live DNS edits, CDN configuration, service deployment, commit or push is authorized by this design alone.
