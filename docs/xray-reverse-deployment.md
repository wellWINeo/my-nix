# Xray reverse-relay deployment runbook

**Status: not deployed.** This is a human-operated cutover, not a consequence of merging the PR. The target configuration is documented in [proxy.md](proxy.md); the [design](superpowers/specs/2026-10-04-xray-proxy-simplification-design.md) and [implementation plan](superpowers/plans/2026-10-04-xray-proxy-simplification.md) explain the invariants. Veles serves the existing client-facing VLESS RAW/gRPC/xHTTP and Hysteria2 endpoints; Buyan retains its public server and initiates two reverse links to Veles. No automatic forward fallback exists. Reserve a maintenance window, console access to both VPSs, an operator-owned public TCP/UDP test destination, and a working client capable of exercising VLESS and Hysteria2 (including UDP). Record each gate's result before proceeding; **stop and restore the previous working state on any failure**.

## Before touching a host

1. Use the same reviewed commit on all hosts; do not deploy an unreviewed working tree. Ensure the machine checkouts have **real** decrypted `secrets/secrets.json` available for evaluation, not `secrets/secrets.dummy.json`. Do not print, stage, or copy the real JSON or private keys into the repository or Nix store. Confirm the installed, root-readable `/etc/nixos/secrets/xray-reality-private-key` exists on Buyan and Veles and that Veles's Hysteria2 certificate/key are installed. Preserve the current secret files; this change does not rotate them. Confirm the public key and selected short ID in Buyan's bridge configuration correspond to Veles's *deployed* REALITY private key and authorized short IDs. The dummy-fixture parity tests cannot establish private/public-key pairing.
2. On a **separate test checkout using dummy secrets**, run `make check` and `bash roles/network/xray/tests/reverse.sh "path:$(pwd -P)"`. For each deployment checkout, verify its revision (`git rev-parse HEAD`) and build before switching: `sudo nixos-rebuild build --flake 'path:.#veles'` or `sudo nixos-rebuild build --flake 'path:.#buyan'`. Preserve the current generation number (`sudo nixos-rebuild list-generations`) and an out-of-band console/recovery path on each host. Keep the resulting `result` symlink out of Git.
3. Verify the **actual binary built for each host**, not a locally installed Xray: from each host's checkout run `xray_pkg="$(nix eval --raw 'path:.#nixosConfigurations.veles.pkgs.xray.outPath')"` (substitute `buyan` on Buyan), then `"$xray_pkg/bin/xray" version`. Record the version. The systemd service injects the REALITY private key from `LoadCredential` into a mode-0600 runtime config and calls that binary with `run -test -format json` before serving. Confirm its test succeeds when each staged service starts (`systemctl is-active xray.service`; inspect `journalctl -u xray.service` locally). Do not dump the rendered config, private key, or credentials into logs or the PR. A flake evaluation is **not** a live Xray binary test.
4. Capture a baseline using a real client: successful Veles RAW, gRPC, xHTTP, and Hysteria2 connections; Buyan public RAW/gRPC/xHTTP; TCP and UDP through the existing relay; observed public source IP. Confirm SSH and SNI-router reachability. Record timestamps, generation numbers, latency and failure counts. If the forward path is already broken, do not assume that the temporary forward stage will preserve service.

## Stage Veles first, without changing its client egress

In a disposable deployment checkout of the reviewed commit **on Veles**, save `machines/veles/default.nix` outside the checkout. Temporarily change *only* `roles.xray.relay.egress.via = "reverse";` to `"forward";`. The portal credentials and inbound RAW/xHTTP settings must remain enabled, so Buyan can connect before the client cutover. Inspect the diff to ensure no other setting changed. Build and run `sudo nixos-rebuild switch --flake 'path:.#veles'`. This forward-only stage is a manual, temporary source override; never merge or push it.

Verify `xray.service`, `nginx.service`, `xray-metrics-collector.timer`, client-facing SNI/ports, Hysteria2 and the prior forward TCP/UDP flow. The new Xray binary's startup test must pass. Watch for a regression compared with the baseline; if present, use the recorded generation to restore the old system and **stop**. Leave the forward-stage source file available for quick recovery.

## Add Buyan's two bridges

On Buyan, from the **unmodified reviewed commit**, build then run `sudo nixos-rebuild switch --flake 'path:.#buyan'`. Verify Xray startup/config validation, `nginx.service`, the public ingress transports and SNI-router, and successful direct Buyan client traffic. Buyan dials Veles on TCP/443 with the existing reverse-only `buyan` UUID over RAW/Vision and xHTTP; it does **not** dial the old forward target from Veles. A failure here must not force Veles client traffic onto reverse: keep Veles forward and roll Buyan back if its own service has regressed.

On Veles, inspect the local, loopback-only expvar endpoint without displaying configuration:

```bash
curl -fsS --max-time 5 http://127.0.0.1:11111/debug/vars |
  jq -r '(.observatory // {}) | to_entries[] | select(.key == "reverse-raw-out" or .key == "reverse-xhttp-out") | "\(.key) alive=\(.value.alive // false) delay=\(.value.delay // "unknown")"'
```

Both **distinct** dynamic reverse tags must appear and become `alive=true`; a successful TCP handshake or a healthy static outbound is not proof of route availability. Allow at least a couple of 60-second probe intervals after bridge registration. If one tag never appears, stays unhealthy, or logs show authentication, route registration, probe, certificate, or REALITY errors, **do not cut over**. Investigate on *both* hosts; do not weaken authentication or introduce a direct fallback. The same data are exported as `xray_observatory_alive` and `xray_observatory_delay_milliseconds` on the proxy dashboard, but dashboards are not a substitute for the end-to-end probes below.

## Rehearse reverse routing (temporary activation, not boot default)

During the maintenance window, restore Veles's source file from the saved **reviewed reverse-mode** copy (not the temporary forward edit). Check that `via = "reverse"`, the two selector tags are `reverse-raw-out` and `reverse-xhttp-out`, and `fallbackTag` remains `blocked-out`. Run `sudo nixos-rebuild test --flake 'path:.#veles'`: this activates the reverse config without making it the boot default. Keep console access open. If the switch or any probe fails, restore `via = "forward"` in the disposable checkout and run `sudo nixos-rebuild switch --flake 'path:.#veles'`; if that fails, restore the recorded previous generation. Never wait for an automatic forward fallback.

Use an authenticated client, not an unauthenticated curl to the relay SNI. For example, from NixPi after its client is upgraded (below), a **TCP-only** check is `curl -fsS --socks5-hostname 127.0.0.1:1081 https://<approved-public-echo-endpoint>/`; compare the returned IP with Buyan's known public egress IP. Also probe Veles RAW, gRPC, xHTTP and Hysteria2 from real clients; test UDP via a UDP-capable proxy client and an operator-owned public UDP echo/DNS endpoint (curl over SOCKS is **not** a UDP test). Check each successful connection's server-side counters or sanitized logs, not merely a 200 response. Public client traffic arriving directly on Buyan must still work independently.

Prove **both** reverse links individually, not just a load-balanced success: in the temporary Veles checkout, change the `reverse-balancer.selector` in `roles/network/xray/relay.nix` to contain *only* `reverse-raw-out`; run `sudo nixos-rebuild test --flake 'path:.#veles'`, wait for that tag's `alive=true`, and repeat the TCP, UDP, source-IP, and client-ingress probes. Observe a counter increase for the selected link and Buyan's corresponding bridge on `/debug/vars` or the proxy dashboard. Repeat with *only* `reverse-xhttp-out`. Restore the original **two-tag** selector and activate it again. These test-only edits are never committed, pushed, or left in the final system generation. If either single-link test fails, restore Veles forward and halt rather than claiming redundant operation.

Verify Buyan's restricted reverse egress: compare the successful public control request with a client request for a **controlled private canary** (for example a temporary listener on Buyan loopback) through the reverse route. The canary must receive **no** connection; inspect restricted-egress routing/logs on Buyan to distinguish a policy denial from an unrelated timeout. Exercise private/loopback, link-local and a name resolving to a private address where safe and possible; do not probe other people's private services. A successful private connection is a stop/rollback condition. Test one-link loss under supervision (temporarily remove one Buyan bridge outbound in a disposable checkout and activate it with `nixos-rebuild test`, then restore it); the remaining link must continue carrying both TCP and UDP. This restarts Buyan's public Xray service, so coordinate the brief disruption. If the temporary config fails its startup test, restore Buyan immediately and halt the cutover.

To verify **both** links lost, briefly stop Buyan Xray (`sudo systemctl stop xray.service`) in the approved window. After the Veles observatory sees neither reverse tag as alive, new Veles requests must fail, not exit directly from Veles or silently use its forward outbounds. Check both TCP and UDP and inspect outbound metrics; an observation lag before declaring a link dead does not prove fail-closed and must not be mistaken for success. Immediately `sudo systemctl start xray.service` on Buyan and require both links healthy again. If such a disruptive test cannot be approved, document it as **unverified** and do not declare the cutover fully validated.

## Final switch and NixPi

Once the rehearsal gates pass, ensure both host checkouts exactly match the reviewed commit (`git diff --exit-code -- machines/veles/default.nix roles/network/xray/relay.nix roles/network/xray/server.nix`); if testing copies were edited, restore them from the saved reviewed versions first. On Veles, build and `sudo nixos-rebuild switch --flake 'path:.#veles'` to make the reviewed reverse configuration the boot default. Recheck two live tags, the four client transports, TCP, UDP, source IP and restricted egress. Do not confuse `nixos-rebuild test` with a durable switch.

Only after Veles and Buyan are stable, build and deploy the same reviewed commit to NixPi (`sudo nixos-rebuild build --flake 'path:.#nixpi'` then `sudo nixos-rebuild switch --flake 'path:.#nixpi'`). Confirm local SOCKS/HTTP ingress, transport selection, TCP/UDP proxy behavior and its existing DNS tunnel. NixPi's client migration should not be used as a substitute for testing Veles with other independent clients. Check Grafana's proxy health panels for the two Veles reverse and two Buyan bridge tags, verify traffic counters move, and monitor reconnects, latency, errors and memory over the following day. Archive only non-secret results and generation IDs.

## Recovery

- **Before final cutover:** keep Veles on the forward-stage generation; if Buyan's new server misbehaves, `sudo nixos-rebuild switch --rollback` on Buyan to the recorded previous working generation. Verify public ingress still works.
- **After final cutover:** first switch Veles explicitly to the staged `via = "forward"` configuration from the disposable checkout, after confirming that forward path still works. If a rebuild is impossible, use `sudo nixos-rebuild switch --rollback` **only after checking** that the immediately preceding system generation is the known-good forward stage. `--rollback` means previous generation, not necessarily pre-PR. Verify client egress and source IP; the older forward route is a manual rollback, never an automatic fallback. If the forward path is unhealthy, do not declare recovery; coordinate outage response via console.
- Restore Buyan to its recorded prior generation if its public service/bridge continues to fail; restore NixPi to its prior generation if its client breaks. The remaining hosts must be validated as a compatible set (old/new configs and credentials). Record generation IDs and incident results. No secret rotation, DNS changes, or MTProxy restoration is performed by this runbook.

Do not merge or deploy solely because the offline checks pass: Xray reverse registration, health selection, both transport data paths, failure behavior and REALITY key pairing require the **deployed** binary and live credentials.
